# Persistent simulation jobs and step state

Real WPS/WRF runs last longer than an HTTP request and must remain understandable after a browser, application or worker restart. `SimulationStore` provides the versioned SQLite persistence required by issues #45 and #46.

## Immutable and mutable state are separate

Every simulation job references exactly one immutable pipeline specification key. The specification freezes:

- validated domain and period;
- deterministic namelists;
- verified ERA5 checksums and provenance;
- pinned runtime identities;
- source revision;
- ordered step contracts.

The SQLite database stores only mutable operational state: queue position, current step, progress, events, artifacts, errors and resource measurements. Scientific inputs are never silently edited inside a running job.

## Database location and migration

The default database is:

```text
workbench-runs/state/workbench.sqlite3
```

A controlled local deployment or test may set:

```text
WRF_CHAMMER_SIMULATION_DATABASE
```

Relative values are anchored at the repository root. SQLite runs with:

- foreign keys enabled;
- WAL journal mode;
- full synchronous durability;
- a 30-second busy timeout;
- versioned schema migrations.

Schema version 1 creates:

- `simulation_job`;
- `job_step`;
- `job_event`;
- `artifact`;
- `input_dataset`;
- `runtime_snapshot`;
- `resource_measurement`;
- `schema_migration`.

## Job creation

Creating a job verifies the immutable specification and materializes:

- one `READY` simulation job;
- every frozen pipeline step as `PENDING` in specification order;
- the verified input-dataset snapshot;
- all pinned runtime snapshots;
- a first structured `job_created` event.

Retry creates a new job linked through `retry_of`; it never mutates the historical failed or cancelled job.

## FIFO queue and worker claim

`enqueue_job()` changes only `READY` to `QUEUED`.

`claim_next_job(worker_id)` uses an immediate SQLite transaction to:

1. select the oldest queued job;
2. assign the worker;
3. start the first pending step;
4. update the job stage;
5. append the event with the next unique per-job sequence.

Two workers racing to claim one job cannot both succeed.

## Pipeline stages

Step IDs from the immutable specification map to user-facing job stages:

| Steps | Job stage |
|---|---|
| input verification, geogrid, ungrib, metgrid | `PREPROCESSING` |
| real | `INITIALIZING` |
| wrf | `SIMULATING` |
| postprocessing, result indexing | `POSTPROCESSING` |

Completing a step atomically marks it `SUCCEEDED` and starts the next one. Completing the final step marks the job `SUCCEEDED`.

A failed current step records a classified code and safe message on both step and job, then marks the job `FAILED`.

## Cancellation and recovery

- `READY` or `QUEUED` jobs become `CANCELLED` immediately; pending steps are cancelled.
- active jobs first become `CANCELLING`; the worker stops its process/container tree and then calls `finalize_cancel()`.
- terminal jobs are never reclassified by repeated cancellation requests.
- after an unclean worker restart, `recover_interrupted_jobs()` marks active jobs and their running steps `FAILED` with `worker_interrupted`, making safe retry explicit.

The store does not claim that an arbitrary WRF checkpoint is resumable. A later executor may resume only from a reproducible step boundary supported by the relevant artifact contract.

## Progress, events and artifacts

Progress is a structured JSON object attached to the current running step. Each update also creates an ordered event.

Events have a unique sequence per job and are appended in the same database transaction as the corresponding state change.

Artifacts store only repository/run-relative paths. Absolute paths, parent traversal and malformed SHA-256 values are rejected. Artifacts may refer to one step or the whole job.

## Resource measurements

Workers can record per-job or per-step measurements:

- CPU seconds;
- maximum resident memory;
- disk bytes;
- wall-clock seconds;
- structured metadata for runtime-specific counters.

Values must be finite and non-negative.

## Current scope

This module implements the persistence and state-machine core. The next slices will:

1. expose job creation, queueing, cancellation, retry and events through the local application API;
2. add the worker loop and process/container executors;
3. parse structured progress from WPS, `real.exe`, `wrf.exe` and postprocessing;
4. persist produced artifacts and resource measurements through these methods;
5. drive the Xaver real micro-run through the same standard path.

No synthetic result or successful state is generated by the store.
